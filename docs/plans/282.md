# Plan: #282 — RefreshSession must not strand the refresh chain

## Objective

`OIDCProvider.RefreshSession` revokes the presented refresh credential and
only then mints the renewed access token and the successor refresh
credential. Any failure after the revoke (`generateJTI`,
`GenerateAccessToken`, `issueRefreshCredential`) leaves the chain revoked
with no successor: the user is silently logged out at the next renewal.

After this change a failed renewal leaves the presented credential
redeemable, and a successful one still leaves exactly one credential the
client holds.

## Design

Mint first, revoke last, compensate on failure:

1. Mint the access token (its JTI, signature and metadata record).
2. Prepare and store the successor refresh record.
3. Revoke the presented credential. This is the last write: nothing after
   it can fail.
4. If step 2 or 3 fails, revoke what steps 1–2 stored (best effort) and
   return the error. The presented credential is still live.

No client can redeem two live credentials at once. Until step 3 has
succeeded, the successor's value exists only in this call's memory and is
never returned. If a compensating revoke fails, the record left behind is
one nobody holds, and it expires.

## Slices

1. This plan.
2. `pkg/iam/oidc_session_refresh.go`: reorder `RefreshSession` and split
   `issueRefreshCredential` into prepare and store steps.
   Tests (`pkg/iam/oidc_session_refresh_rotation_test.go`), using a
   fault-injecting `TokenStorage` over `MemoryStorage`, with a failure at:
   - storing the access-token record,
   - storing the successor refresh record,
   - revoking the presented credential.
   Each test asserts that the call fails, that the presented credential
   still renews afterwards, and that no credential minted by the failed
   call stays live.

## Out of scope

- Two concurrent redemptions of the same credential (a check-then-revoke
  race). Closing it needs a guarded revoke (CompareAndSwap on the token
  record) that the `TokenStorage` interface does not expose yet. Reported,
  not fixed here.
- `docs/SPEC.md`: nothing in it names this behaviour, so it stays as it is.
