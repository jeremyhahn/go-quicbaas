# Plan: #1700 integration suite, main fix (PR #2427)

## Objective

Make `make integration-test-init` (the init backend matrix: every backend
crossed with every transport) green on main, one slice per lane session,
each slice a CA-ruled defect the matrix surfaces.

## Slices in order

1. Done before this plan: the cluster builder's clients act as the tenant
   operator; the passkey login hint is the enrolled admin's email; every
   matrix cell logs in as the first-boot admin and MCP liveness carries its
   session; the ceremony E2E's CLI trusts the CA chain first boot wrote.
2. MCP `data put` reaches quicbaas's entity KV tools (CA ruling 574 item 1,
   option a). On a full node `qrdb_put/get/delete/list` are go-qrdb's own
   key/value tools (`key`/`value`); quicbaas's entity tools of those names
   are left off the node (`qrdbNativeDuplicateTools`). Register the same
   entity tools also as `quicbaas_kv_put/get/delete/list`
   (`addKVEntityTool`, pkg/api/mcp/tools.go), each on the existing
   `kv:put/get/delete/list` permission (no new permission, no role
   widened), and point the SDK MCP transport's `ToolName` at them. The
   transport also decodes their results into the `service.*Response` types
   the KV client accepts (it answered "invalid response type" on a map)
   and sends List paging as `pageSize`/`pageToken` (sdk kv_handler.go).
   Tests: `TestModuleTools_EntityKVToolsOnExistingKVPermissions`,
   `TestInvokeTool_EntityKVPutReachesEntityHandler` (pkg/api/mcp);
   `TestTransport_Request_KVPutReachesEntityTool` and the KV rows of
   `TestTransport_MapToToolName` (sdk/go/transport/mcp); the agent-session
   floor test admits `quicbaas_kv_get/put/list` on the same grants.
3. Sealed (shamir) init cells. A sealed node runs quicbaas's own
   sealed-window listeners until its officers unseal it; go-qrdb's unified
   server (QUIC, MCP) only comes up after unseal.
   - grpc/unix: the sealed gRPC server registers quicbaas.v1.QuicBaaS over
     the sealed-window facade, so the allowlisted Health answers (re-applied
     from lane sql, row/1801-shamir-sealed-transports;
     `TestSealedBoot_GRPCServesQuicBaaSHealth`).
   - quic: the REST server gains an `HTTP3` option serving the same router
     (and sealed gate) on the UDP side of its address; the sealed REST
     listener turns it on whenever it serves TLS
     (`TestSealedBoot_QUICServesHealth`).
   - mcp: blocked on a CA ruling. The cell logs in with the first-boot
     admin's `admin/admin.crt`, which a sealed shamir node never has; MCP
     refuses an uncredentialed session (ruling 571); and the sealed-window
     table maps no MCP tool to the health verb. A sealed MCP listener alone
     cannot make the cell pass.
4. Next slices: whatever the init matrix still fails, one CA-ruled defect
   per slice.

## Out of scope

- MCP authentication (ruling 571: unchanged).
- `qrdb_scan` (no tool of that name is registered on any surface).
- Any new permission or role change.
