# #226 — non-argv path for `--so-pin` / `--user-pin`

## Objective

Every CLI verb that sends a Security Officer or User PIN on its request can
take it without argv, with several secrets on one invocation (ruling 191:
take the triage recommendation; PINs read into protected memory).

## Slice 1 (this lane)

- `cmd/quicbaas/pin_input.go`: per-PIN sources in precedence order —
  `--so-pin-file` / `--user-pin-file` (path, `-` = stdin), then
  `QUICBAAS_SO_PIN` / `QUICBAAS_USER_PIN` (as `quicbaasd init`; SO also
  `QUICBAAS_BARRIER_SO_PIN`), then the compatibility argv flag. Each read
  lands in a `secure.Buffer` first. Stdin may be claimed by one secret only
  (passphrase-stdin included).
- Wired into `barrier init`, `init-shamir`, `rekey`, `recovery generate`,
  `init initialize`, `init sign-csr`; help examples no longer show a PIN on
  argv. `barrier init --barrier-strategy none` ignores leftover PIN env.
- Tests (`pin_input_test.go`): file + stdin PINs reach the request, env beats
  argv, double stdin claim refused, empty file refused, `none` ignores env,
  every PIN verb has the `-file` flag.
- Docs: `docs/barrier/cli.md` §3a.

## Out of scope

- Removing the argv `--so-pin` / `--user-pin` flags outright (kept, as for
  `--passphrase` and `barrier seal --so-pin`, for compatibility).
- `barrier seal` (already has `--so-pin-stdin`, #491).
- The SDK request fields stay `string` (#237).
