# Plan: #1726 sdk/backup Restore keeps its source and reads a running restore right

## Objective

`backup.Client.Restore` never sends a request the service refuses after the
client accepted it, and never reports a running restore as a failed one.

Findings: the backup service (`pkg/service.RestoreBackupRequest`) restores by
backup ID only; neither REST, gRPC nor the embedded transport carries a
source. The service restore is asynchronous: it returns a job id and status.

## Slices

1. Client (one commit, ported from lanes 1722a-d, which never reached main):
   - `validateRestoreRequest` refuses a request that sets `Source` and one
     without `BackupID`, with a typed invalid-input error, before any call.
   - `Restore` sends `*service.RestoreBackupRequest{BackupID}` and maps the
     `*service.RestoreBackupResponse` into `RestoreResponse{Restored, JobID,
     Status}`; `Restored` only for status `completed`.
   - MCP transport routes `quicbaas.Backup/Restore` to the same service types.
   - Tests: client unit tests (source-only refused, missing ID refused,
     running restore returns job id and status, completed sets Restored);
     embedded, REST and MCP transport tests through the real client.
   - changelog.d entry (callers see the new fields and the refusal).

## Out of scope

- A polling API for restore progress.
- Adding a source to the service, REST or gRPC restore requests.
