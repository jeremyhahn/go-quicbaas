## SPEC row text (for `docs/SPEC.md`, replacing the one-line row)

Requirements cell, `<br>`-separated:

- Declarative workload placement: go-quicbaas's own scheduler places workloads (owner ruling 191), on the scheduler's placement engine (`pkg/scheduler/placement`) and the fleet registry and admission (`pkg/orchestration`)
- A placement spec maps each role (agent, ci, review, …) to a host count or to named hosts, per tenant, and the operator tunes it as hosts join (the owner's shape: two hosts for agents, five for PRs and code reviews). Edits are ordered by a generation compare-and-swap, so a racing edit is refused, never lost
- Each role has a resource profile measured from its runs, not assumed (agent about 0.02 core and 3.4 GiB, CI 3 to 4 cores). Admission divides a host's measured room by the profile of the role it places
- A read-only drift report compares the spec with the work running and the hosts enrolled. It is exhaustive by construction: a spec field with no drift rule fails construction
- An actuator reconciles running workers against the spec and scales a role up or down with no hand-edited runner configuration. Fungible roles (ci, review) move on their own after the destination passes admission. A move of agent work needs a person's consent, and every move the actuator orders is recorded
- Admission sees every host before it assigns work: work goes to a host with measured room, never to whichever host polls first
- Credential custody is part of placement: an agent host's AI-account credentials are held in go-xkms KMS custody with strict refresh rotation, one lineage per host. Adding an agent host is a declaration plus at most one human consent step. Until that custody seam lands, the actuator moves only ci and review, and an agent-role declaration is reported as drift, never actuated
- The placement verbs are served through `sdk/go` on all six transports and the CLI
