# Plan: batch put and delete with no tenant answer 403 / PermissionDenied

Row issue: #1800. PR: #2408.

## Objective

A batch put or delete with no tenant bound is refused as a forbidden
request, the way single-item operations are, instead of being reported as
invalid input: gRPC answers `PermissionDenied` and REST answers 403.

## Slices, in order

1. Service (done): `batchKeyError` in `pkg/service/quicbaas.go` passes an
   `ErrForbidden` error from `BuildKey` through unchanged and wraps any
   other key error as `ErrInvalidInput`. BatchPut and BatchDelete use it.
   Tests in `pkg/service/batch_tenant_test.go`:
   - TestBatchPut_NoTenantIsForbidden, TestBatchDelete_NoTenantIsForbidden
   - TestBatchPut_ReservedEntityTypeStaysInvalidInput and its BatchDelete
     twin, TestBatchDelete_ReservedEntityTypeStaysInvalidInput
2. Transport proof (tests only):
   - `pkg/api/grpc/server_batch_tenant_test.go`:
     TestServerBatch_NoTenantIsPermissionDenied (BatchPut, BatchDelete) and
     TestServerBatch_InvalidEntityTypeStaysInvalidArgument
   - `pkg/api/rest/handlers_batch_tenant_test.go` (`rest` tag):
     TestHandleBatch_NoTenantIsForbidden, with 403 rows for the tenant
     refusal and 400 rows for an invalid-input error, on both handlers

## Out of scope (follow-ups)

- BatchGet reports per-item failures as `Found: false`, so a missing tenant
  is not surfaced as 403 there.
- StreamBatchPut returns the error as a string in its response.
