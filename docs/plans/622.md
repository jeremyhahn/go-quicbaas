# Plan #622: delete the `canned` workflow mode

## Objective

`WorkflowModeCanned` is declared and documented but never implemented: the
lead decomposes the task in every mode. Ruling 189 (DS-3821, 2026-10-26):
implement it only if the SPEC row names it, otherwise delete it. The
`orchestration` row of `docs/SPEC.md` does not name a canned mode, so the
mode is deleted.

## Slices

1. **Delete the mode** (one commit).
   - `pkg/orchestration/workflow_types.go`: drop `WorkflowModeCanned` from
     the constants and from `validWorkflowModes`; `Validate` refuses an
     unknown mode with a message that names the modes that exist
     (`constrained`, `autonomous`).
   - `pkg/orchestration/control_loop.go`: the constrained-mode checks no
     longer mention canned.
   - `sdk/go/client/orchestrator`: drop the SDK's `WorkflowModeCanned`.
   - Workflow wizard (`WorkflowWizard.svelte`): no `canned` option.
   - Tests that used canned as a sample mode use `constrained`.
   - Tests added: `Validate` refuses `mode: canned` and the error names
     `constrained` and `autonomous`; the workflow loader refuses a YAML
     workflow with `mode: canned`; a constrained workflow still runs with
     `DecomposeTask` called.
   - Docs: `docs/orchestration/engineering.md` lists two modes and says
     `canned` is refused; changelog entry for the orchestration feature.

## Out of scope

- A predeclared-work-items workflow (the "implement" branch of the ruling).
- Rebuilding committed frontend `dist/` bundles beyond what the Makefile's
  own frontend target produces.
