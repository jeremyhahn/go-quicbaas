# Plan: #2538 barrier verbs over REST carry the platform bearer

## Objective

`Security().Barrier()` over REST used go-qrdb's REST sub-client, whose
`http.Client` cannot send the platform bearer, so the node answered 401
(`TestBarrierStatus/rest/BarrierStatus`). Over REST the barrier verbs now
ride the SDK REST transport, which sends the bearer set by `WithAuthToken`,
and keep the refusal shape go-qrdb's client gave the CLI.

## Slices

1. (PR #2543, done) `sdk/go/transport/rest/barrier_client.go`: a
   `BarrierClient` on the SDK REST transport with go-qrdb's methods, paths,
   bodies and response types; `sdk/go/services.go` returns it for
   `*rest.Transport`; the SO PIN guard wraps the REST transport's client.
   Tests: `TestBarrierStatus_REST_SendsPlatformBearer`,
   `TestBarrierClient_MethodPathAndBearer` and the wire and SO PIN tests.
2. (this lane) PR #2543's Integration job was red. A refused barrier verb
   came back as a bare SDK error, so the CLI printed the server's message
   with no status. `TestBarrierAuthPosture_DefaultDeny` asserts "401" for a
   token-less REST seal. The client now returns
   `*qrdbtransport.RequestError{Method, StatusCode, Err}` around the SDK
   error, as go-qrdb's client did (a 501 wraps
   `CapabilityUnsupportedError`). `Transport.sendRawRequest` hands back the
   status; `doRawRequest` is unchanged for every other caller.
   Test: `TestBarrierClient_ErrorKeepsVerbAndStatus`.

## Out of scope

- Server, auth and RBAC changes; other REST sub-clients of go-qrdb.
- The CLI integration suite needs Docker, so CI runs it.
