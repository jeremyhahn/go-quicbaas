# Plan: #1894 Separate certificate common names from SPIFFE workload names

## Objective

Codex review 7420 P1 5 on #1845: with a SPIFFE trust domain configured, the CA
uses the subject CommonName as the SPIFFE SAN's workload name and refuses a
CN that is not a SPIFFE path segment, so a client certificate or CSR for
`admin@example.com` fails. The subject CN must be kept as requested and the
CA given a separately derived, valid workload name (`SPIFFEName`).

## Slices

1. Failing test first: `pkg/server/ca_service_adapter_spiffe_name_test.go`
   issues a keypair and signs a CSR with CN `admin@example.com` on the real
   software CA with a trust domain set, for a tenant and for the system
   tenant. Before the fix both fail (the CA refuses the CN as a path
   segment).
2. Fix: `service.SPIFFEWorkloadName` (in `pkg/service/certificate_service.go`)
   escapes every byte outside letters, digits, `.` and `-` as `_` plus two
   lower-case hex digits (injective; a valid segment without `_` is kept).
   `service.CSRCommonName` reads a CSR's CN. The pkg/server adapter and the
   REST CA servicer set `SPIFFEName` from them on the keypair and CSR paths.
   Unit tests for both helpers in `pkg/service`, and the REST servicer's
   SPIFFE option tests assert the name.

Re-lands the starting point 7d1d615d9 (branch `issue/1814cf`) onto main.

## Out of scope

- Any go-xkms change: the pinned SDK already carries `SignOptions.SPIFFEName`
  and `CertificateRequest.SPIFFEName`.
- Changing which requests carry a tenant (the system-tenant retention itself).
