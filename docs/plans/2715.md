# Plan: #2715 MCP key-value expectedVersion

## Objective

An agent that reads a key, decides, and writes it back can overwrite another
writer's change that landed in between. The MCP key-value put and delete
tools take an optional `expectedVersion`: a stale version (an absent key has
version 0) fails with a version conflict and changes nothing, and omitting
it keeps today's unconditional write.

## Slices, in order

1. `expectedVersion` on the put and delete tools (`qrdb_put` /
   `quicbaas_kv_put`, `qrdb_delete` / `quicbaas_kv_delete`). The service
   decides it with one go-qrdb transaction holding a
   `CompareVersion`/`CompareEqual` compare and the write as its success op;
   a failed compare is `ErrConflict` with a `*KVVersionConflictError` cause,
   which reaches MCP callers as `MCPResourceConflict`. A value above
   `math.MaxInt64` is refused as a conflict. The Go SDK key-value client
   refuses the field, since no SDK transport carries it. Tests:
   pkg/api/mcp/tools_kv_expected_version_test.go `TestKVExpectedVersion_*`
   (real in-memory qrdb node), pkg/service/kv_expected_version_test.go
   `TestKVService_ExpectedVersion_RefusesOutOfRange`,
   sdk/go/client/kv/expected_version_test.go
   `TestKVClient_RefusesExpectedVersion`.
2. Follow-up: report the real stored version from get and from the
   unconditional put (needs the MVCC read capability).

## Out of scope

- `expectedVersion` on REST, gRPC or QUIC.
- `expectedVersion` on the batch and transaction tools, or any other tool.
