# #213 — a published park reason carries no subprocess output

## Objective

Ruling 189 (DS-3821): a park reason posted to a forge issue carries a
structured, non-sensitive summary of a failed subprocess, never its output.
Regex redaction fails open on secret shapes it does not know, so it can no
longer be what makes subprocess output publishable.

## Design

- The only producer that put subprocess output into a published reason is
  the review-round escalation after failed verification
  (`runner.go` `nextRoundWithEvidence` <- `verificationFailureEvidence`).
- The summary has fields that are never drawn from the output itself:
  the command's name (configured by the operator), its exit status, how many
  bytes of output were withheld, and the job whose audit record holds them.
- Where the raw output is kept: the job's `sdlc:verification` audit record
  (`auditVerificationResults`), which already carries each failed command's
  failing lines. The operator who takes the escalation reads it there; the
  summary names the job and the record, so the park still points a person
  at the cause (#198).
- The worker still gets the full failure in its feedback prompt. That channel
  is internal, not a publication.
- `publicOutput` stays as the bound for AUTHORED text (the worker's own words,
  an assessment, a forge adapter's error), and its doc no longer claims to
  make subprocess output publishable.
- Non-internal forge: the answer is the same. Nothing about this summary
  depends on the forge being private.

## Slices

1. `pkg/sdlc/public_reason.go`: `publicCheckSummary` and
   `publicVerificationSummary(jobID, failed, budget)`; the escalation uses it;
   `verificationFailureEvidence` and `verificationExcerpt` go.
   Tests: a failed command whose output holds an unrecognised secret shape
   escalates without that secret in the park reason (fails before), while
   the reason still names the command, the exit status and the audit record;
   the budget still holds when many commands fail.
2. `docs/SPEC.md`: the sdlc row states the rule.

## Out of scope

- Error strings that carry `diagnosticTail` (`PublishCommandError`,
  `CheckoutCommandError`, `MergeResultConflictError`). Their audience is the
  daemon log and the task record. Any path that publishes them is a follow-up.
- #210 and #199: when a park may speak at all.
