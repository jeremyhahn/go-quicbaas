# #1909 Preserve SSH cloning when the key service is remote

## Objective

Codex 7453 P1 11 (PR #1845 head 08f0210): with seal disabled and `xkms.url`
naming a remote sealed xkmsd, `wireProjectWorkspaces` must still give the
managed-workspace `GitProvisioner` a host-key pin store. A nil `HostKeys`
makes `pkg/service/project_git.go` refuse every SSH clone.

## Finding vs main

On main, `pkg/server/lifecycle_project_workspaces.go` composes the pins
from an independent file store under `<projects root>/.hostkeys`
(`xkmsssh.NewFileStorage` + `NewHostKeyStore`), not from a barrier-backed
store, so the remote-xkms setup keeps working. The barrier-only pin store
the finding names exists only on #1845's head, which main does not contain.
What main lacks is the coverage the finding asks for.

## Slices

1. Regression test `pkg/server/lifecycle_project_workspaces_test.go`:
   - `TestWireProjectWorkspaces_RemoteXKMSKeepsSSHCloning`: a server with no
     QRDB node (no barrier) and `xkms.url` set builds the remote REST client;
     wiring gives the provisioner a signer and a non-nil `HostKeys`, and the
     pin directory exists under the projects root. Fails when the pins are
     made to depend on a local barrier (the #1845 shape); passes on main.
   - `TestWireProjectWorkspaces_NoSSHClient`: no SSH client gives no SSH auth.

## Out of scope

- Changing #1845's branch: if it lands its barrier-only pin store, this
  test goes red and that PR must keep the file pin store (or a backend that
  works with remote xkms).
- go-qrdb / go-xkms changes: none needed.
