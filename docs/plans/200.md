# #200 — a stale session-metadata tail must not let an append overwrite a stored event

## Objective

`KVSessionEventLog.Append` rolls the metadata's `LatestSequence` forward in a
second write whose failure it discards. `LatestSequence` trusted that record
whenever it existed, so after one failed roll-forward the next append was
assigned (and validated against) a sequence that already held an event, and
`kv.Put` overwrote it — the terminal `KindSessionClosed` included.

## Shape (ruling 191: the coordinator's recommendation)

Two independent guards, so the collision is impossible rather than merely
unlikely:

1. **Metadata is a hint, the events are the truth.** `LatestSequence` starts
   at `meta.LatestSequence` and probes `eventKey(hint+1)`, `hint+2`, … until
   it finds an unoccupied key. In the healthy case that is one extra `Exists`.
   A stale record therefore yields the real tail, so `AppendNextSessionEvent`
   assigns the next free sequence and `Append`'s gap check rejects a reused
   one. The next successful append rewrites the metadata, repairing it.
2. **The event write cannot overwrite.** When the injected KV offers
   `PutIfAbsent` (the `guardedCreator` capability `NewAccountStore` already
   asserts), `Append` writes the event key with it, and an occupied key fails
   with `ErrSessionLogGap` instead of replacing the event. A store without the
   capability keeps the plain `Put`, still protected by guard 1.

The roll-forward write stays non-fatal: the event is durable and the tail is
derived from the events, so reporting it as an append failure would invite a
retry of an append that succeeded.

## Slices

1. This plan; the fix in `pkg/orchestration/session_log_kv.go`; tests in
   `pkg/orchestration/session_log_kv_test.go`:
   - metadata write fails after a session's events, then appends continue
     through `AppendNextSessionEvent`; every stored event survives and the
     terminal `KindSessionClosed` is still last and intact;
   - `LatestSequence` reports the events' tail when the metadata is behind;
   - a guarded store refuses an append onto an occupied sequence.

## Out of scope

- #201 / #249 (other multi-key partial writes): same family, separate rows.
- Retention bookkeeping carried on a metadata write that failed: the prune
  catches up on the next successful roll-forward.
