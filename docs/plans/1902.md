# Plan #1902: grant the embedded principal the Security permissions delegations must narrow

## Objective

Codex 7453 P1 2 (PR #1845, `pkg/qrdbservice/qrdbservice.go:38`): go-qrdb
v0.51 computes a delegation's effective grants as the intersection of its
certificate scope with the embedding principal's registered grants. The
principal's grant list omits `keys:encrypt`, `keys:sign`, `certs:issue`,
`trust:read`/`trust:write` and other permissions the embedded Security
operation map requires, so a valid tenant delegation granting
`keys:encrypt` still cannot call `Security().Crypto().Encrypt`.

## Status: blocked on #1845 (the go-qrdb v0.51 re-pin, #1816)

- main pins `github.com/jeremyhahn/go-qrdb v0.30.1-alpha`; v0.30.1 has no
  delegation intersection and `pkg/qrdbservice` does not exist on main.
- The cited code lives only on the #1845 train (seen on `issue/1140c`,
  pinned to v0.51.0-alpha). The issue's scope is "on main after #1845
  merges". Resume this lane once #1845 is on main.

## Slices (after #1845 merges)

1. Failing test first (m1237): start a real in-process node
   (`pkg/testutil/qrdbnode`), issue a tenant delegation whose scope grants
   `keys:encrypt`, and call `Security().Crypto().Encrypt` through the node's
   real `DelegatedContext` (no binder that fabricates `ScopePermissions`).
   Expect success; it fails on the current grant list.
2. Fix: derive the embedded principal's grant ceiling from the embedded
   Security operation map (every permission it names: keys, certs, trust,
   ...), so the ceiling cannot drift from the map. Keep the intersection:
   the delegation still narrows to its certificate scope.
3. Negative test: a delegation without `keys:encrypt` is still refused
   (the intersection holds); a test that every permission in the Security
   operation map is in the principal ceiling.
4. Transports: the Security calls the finding names, through gRPC, REST and
   MCP (`make integration-test-<feature>` for the touched feature).
