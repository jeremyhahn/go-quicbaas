# Plan: #1321 one client trust-anchor set (option (c))

## Objective

`iam.piv_login.ca_file` and `iam.mtls.tls_client_auth_ca_file` never reached the
live TLS listener: `buildRESTServer` added both pools to a clone of
`s.tlsConfig` that no listener serves. The ruling (CA m579 item 9, option (c);
m599) removes both options. A client CA is trusted only if it is in
`security.tls_ca_file` (or is the platform CA), on every transport, and the old
keys are refused at load with a typed error that names `security.tls_ca_file`.

## Slices

1. Port the option (c) work from `train/dn` (lane 1318a/1318b/1318c, never
   merged to main) onto current main:
   - `pkg/server/client_trust_anchors.go`: one trust-anchor set loaded from
     `security.tls_ca_file` into the shared `s.tlsConfig.ClientCAs`, with no
     change to `ClientAuth` (a `RequireMTLS` node keeps requiring a cert).
   - drop `appendOperatorClientCAsFn`, `appendPIVClientCAsFn` and the clone
     in `lifecycle_rest.go`; the PIV verifier uses the same anchor set.
   - `pkg/config`: the two removed keys refused at load (typed error).
   - Tests: `client_trust_anchors_test.go` (handshake on the shared config
     accepts a cert from a CA in `security.tls_ca_file`, refuses one from a CA
     that is not; `RequireMTLS` still requires a cert),
     `lifecycle_client_ca_test.go`, `loader_removed_ca_keys_test.go`.
   - docs (iam, certificate-authority), integration yaml without the old
     keys, `changelog.d` entry (callers see the removed keys).

## Out of scope

- Per-route chain verification (option (b)).
- Any change to which transports share `s.tlsConfig`.
