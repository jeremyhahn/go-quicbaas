# Plan: #201 — a CLOSED record whose session log never ended is repaired

## Objective

A durable session record that says CLOSED while its session log does not
(metadata still ACTIVE, or CLOSED metadata with no `KindSessionClosed`) has the
missing log transition completed: at daemon boot, and again whenever an
operator's `CloseSession` lands on such a record.

## Where the tree stands

`finishDurable` now writes the log first and the store record last, so a
conclusion that fails on the log leaves the record ACTIVE and the boot pass
concludes it again. The residual the issue names — CLOSED record, unended log —
is still reachable from records written by a daemon that ran the store-first
order, from any writer that closes a record without the conclusion path
(`UpdateSessionStatus`), and from a log whose write was lost after the record
closed. Nothing reads such a record's log again: `LoadPersistedSessions` skips
closed records, and `CloseSession` answers success off one.

## Repair shape (ruling 191: the recommended shape)

- Boot scan: `LoadPersistedSessions` already lists every record; for each
  CLOSED one it runs `repairConcludedLog`. The added cost is one `GetMeta` per
  closed record, plus one latest-event read when the metadata is CLOSED. A
  record whose log has no metadata costs only the `GetMeta`.
- Lazy: `CloseSession` on a CLOSED record runs the same repair before it
  answers success, so a repair that failed at boot is retried by the next
  operator close.
- The repair is `concludeLog` itself (gate first, then the ending), under the
  record's own `ConclusionReason`; a record with none is attributed
  `reconcile`. A record still live in memory is left to its live conclusion.
- A failed repair at boot is logged and does not stop the boot; on
  `CloseSession` it is returned as ErrAgentServiceUnavailable.

## Slices

1. `repairConcludedLog` in `session_conclusion.go`, called from
   `LoadPersistedSessions` and `CloseSession`. Tests
   (`session_log_repair_test.go`): a restarted service over a CLOSED record
   with ACTIVE log metadata, and over CLOSED metadata with no ending, writes
   the ending under the record's reason; an already-ended log gets no second
   ending; a log with no metadata stays empty; `CloseSession` on a CLOSED
   record with an unended log writes the ending.
2. docs/SPEC.md orchestration row: no wording change needed (it names the
   durable log, not this repair).

## Out of scope

- The job audit (`recordSessionConclusionOnJob`) for such records: the
  issue is the log's ending only.
- A pending-conclusion marker or an age/count bound on the boot scan.
- #200 and #249 (same family, other keys).
