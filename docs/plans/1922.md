# Plan: #1922, the authorization endpoint refuses a client in another tenant

## Objective

`OIDCProvider.Authorize` (`pkg/iam/oidc.go`) never issues an authorization
code to an end user whose tenant differs from the client's tenant. The
refusal is a typed error (`AuthorizeTenantMismatchError`) carrying
`access_denied`, and it is raised only after the client and its redirect URI
are validated, so the REST handler redirects it to the client with the state
and no code (RFC 6749 §4.1.2.1). An unknown client or an unregistered
redirect URI is still answered directly and never redirected.

## Slices

1. Plan (this file).
2. The tenant check and its tests:
   - `pkg/iam/errors.go`: `AuthorizeTenantMismatchError` wraps an
     `access_denied` `OAuthError`; its description names neither tenant.
   - `pkg/iam/oidc.go`: once the client, redirect URI and request are
     validated and an end user is on the request (`UserID != 0`), a
     `TenantID` that differs from the client's (an empty one included) is
     refused.
   - `pkg/iam/oidc_authorize_tenant_test.go`: other-tenant user refused (it
     gets a code on the base), no-tenant user refused, same-tenant user gets
     a code, other-tenant user with a bad redirect URI still gets the direct
     error.
   - `pkg/api/rest`: the typed refusal is redirected to the client with
     `error=access_denied` and the state, and no code.
   - `docs/iam/oauth21-conformance.md`: a §4.1.2.1 row for the refusal.
   - `changelog.d/iam.md`: callers see the refusal.

## Out of scope

- #1461 (the REST handler authenticating the end user through the inherited
  auth chain and setting `UserID`/`TenantID`). Until it lands the REST
  handler puts no end user on the request, so the check is reached only by
  callers that set one; once #1461 sets them, every REST request is checked.
- Cross-tenant checks at the token endpoint (code exchange, refresh).
