# Plan: #1885 signalbridge: Stop right after Run starts is a no-op

## Objective

`OrchestratorBot.Stop` stops a bot whose `Run` has just started: a `Stop`
that lands as soon as the bot counts as running makes `Run` return, even
when the parent context is never cancelled.

## State found

The fix already landed on main in #2236 ("store the run cancel func before
the bot counts as running", Refs Gitea #1881, the issue this one migrated
from):

- `Run` (`pkg/signalbridge/bot.go`) sets `running` and stores the cancel
  func under `cancelMu`, so `Stop` never sees a running bot without a
  cancel func.
- `TestBot_StopAsSoonAsRunning` (`pkg/signalbridge/bot_test.go`) lands a
  `Stop` through the `onRunning` hook, in the window between `running`
  and the cancel func, with `context.Background()` as parent, and asserts
  `Run` returns.

## Slices

1. Verify: run `TestBot_StopAsSoonAsRunning` (and `TestBot_DoubleRun`)
   under `-race -cpu 1,2 -count=500`, the issue's verification bar. No
   code change unless it fails.

## Out of scope

- Other signalbridge lifecycle changes.
- `make integration-test-signalbridge` needs Docker (docker-compose
  stack); this container has none, CI runs it. No code changes here, so
  it is not affected anyway.
